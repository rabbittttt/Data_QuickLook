- 审计日期：2026-11-22
- 审计范围：当前仓库全部源码（后端 `server.py`、`warehouse.py`、`excel_parser.py`、`shared_sync.py`、`source_paths.py`、`runtime_paths.py`、`workspace_relocation.py`、`analysis_engine.py`、`comparison.py`、`app.py`、`scripts/`、`启动数据速查.cmd`；前端 `web/` 全部 JS/HTML；vendored 依赖 `web/vendor/`；构建、迁移脚本与测试）
- 方法：全量人工代码审读 + 关键疑点动态验证（错误消息格式、依赖版本、API 调用方排查）+ 测试基线回归
- 严重级别定义：P1 = 需立即修复的安全/数据破坏问题；P2 = 明确缺陷，应尽快处理；P3 = 健康度/健壮性/一致性问题

## 总体结论

未发现 P1 级问题。代码整体质量较高：SQL 全部参数化或安全转义、静态服务对目录穿越做了防护、上传采用"临时文件 → 完整校验 → 原子发布"且覆盖确认绑定文件真实状态而非文件名、工作表 XML 拒绝 DTD（防 XXE）、发布链路有清单与 SHA-256 校验，测试覆盖面广。本次审计发现 **4 项 P2、10 项 P3**，集中在：依赖版本陈旧、删除上传文件后的永久性报错、搜索/解析两条路径的性能与资源风险，以及错误处理的健壮性。

测试基线（本次审计实测）：
- Python：`python -m unittest discover -s tests` → **89 项全部通过**（259.6s）
- Node：`tests/test_*.cjs` 共 12 个文件 → **全部通过**

## P2 发现（应尽快处理）

### P2-1 已删除的上传文件会在每次同步时重复报错，且没有任何清理机制
- 位置：`warehouse.py:137-143`（`register_upload`/`uploaded_files`，全库无 `DELETE FROM uploaded_files`）、`warehouse.py:27-29`（`file_signature` 直接 `stat()`）、`warehouse.py:151-169`（`sync_files` 捕获后追加 errors）
- 问题：上传文件记录写入 `uploaded_files` 表后，如果用户在资源管理器中删除或移动了该文件（或整个 `uploads/` 目录被移动），后续每次同步都会因 `path.stat()` 抛 `FileNotFoundError` 被记入 `STATUS['errors']`，且记录永远不会被移除。共享目录侧（`shared_sync.py`）有 `visible` 过滤处理此情况，但上传侧没有。
- 影响：同步状态长期显示"N 个文件同步异常"，前台提示无法通过任何操作清除，掩盖真实错误。
- 建议：`sync_files` 遇到 `FileNotFoundError` 时清理 `uploaded_files` 中对应记录（保留 `datasets` 数据，与"原文件不可用，仍可查看已入库数据"的产品语义一致），并补充回归测试。

### P2-2 vendored ECharts 5.5.0 落后多个安全修复
- 位置：`web/vendor/echarts.min.js`（实测 `version:"5.5.0"`）
- 问题：5.5.0 存在已公开的安全修复未吸收——图例数据处理相关 XSS 于 5.5.1 修复（2024-06）；Lines 系列提示框 XSS（CVE-2026-45249）在 6.1.0 修复。
- 影响：本项目图表的系列名、轴标签、图例文本直接来自 Excel 单元格内容，属于数据驱动渲染路径。项目当前未使用 `lines` 系列，图例 formatter 也返回纯文本，实际可利用性有限，但"打开恶意 Excel → 前端渲染"的链路值得收敛。
- 建议：升级 vendored 库至 6.1.0 或更高（至少 5.5.1），并在 `web/vendor/NOTICE.md` 记录版本与升级日期；升级后跑一遍 `tests/test_*.cjs`。
- 参考：Apache ECharts 5.5.1/6.1.0 release notes（本次经 web 检索核实，详见报告末尾来源）

### P2-3 `/api/search` 对全库做无限制的全量扫描
- 位置：`server.py:512-527`
- 问题：每次搜索请求对目录中的每张表执行 `STORE.load()`（整表从 SQLite 读入 DataFrame）并逐行做子串匹配；无缓存、无行数上限、无并发限制。前端输入框 450ms 防抖后即触发一次。
- 影响：数据量增长后，每次按键可能触发秒级甚至分钟级的全表 IO+CPU；多个标签页同时搜索会叠加。ThreadingHTTPServer 下还会与同步等操作争用资源。
- 建议：优先用 `catalog` 的文件/表/字段名做轻量命中；单元格内容搜索限定在中小表或加行数阈值；对结果做短 TTL 缓存；超限时返回"数据过大，请细化关键词"。

### P2-4 `discover_tables` 以完整内存模式加载工作簿，且解析期间持有全局锁
- 位置：`excel_parser.py:204`（`load_workbook(..., read_only=False)`）、`server.py:91`（`sync_worker` 持有 `LOCK` 调用 `STORE.sync_files`）
- 问题：每次同步将整个工作簿（含样式、合并信息）以 openpyxl 常规模式载入内存，内存放大倍数高；解析期间持有 `LOCK`，所有需要该锁的请求（导入覆盖判定、识别规则保存）都会阻塞。此外解析依赖 openpyxl 私有 API：`worksheet._cells`（`excel_parser.py:88`）与 `sheet._get_source()`（`server.py:342`）。
- 影响：大工作簿（README 允许 256 MiB 上传）同步时可能出现显著内存峰值与长阻塞；openpyxl 升级（当前 3.1.5）随时可能破坏私有 API 调用。
- 建议：评估 read_only 流式识别（上传校验路径已经这样做了）；至少在文档中标注内存预期；为私有 API 用法加防御性兼容层（try/except + 回退）。

## P3 发现（健康度与健壮性）

### P3-1 所有异常统一返回 400 且直接回传 `str(exc)`
- 位置：`server.py:543-545`（GET）、`server.py:602-603`（POST）
- 问题与影响：
  - 内部错误（磁盘满、权限、数据库损坏）与用户输入错误不可区分，前端无法针对性提示；
  - `str(exc)` 可能向页面回传绝对路径等内部信息（本机工具影响小，门户部署时应注意）；
  - 实测 `str(StopIteration()) == ''`：`server.py:529`（`/api/raw`）与 `server.py:585`（`/api/recognition`）的 `next(...)` 在 id 不存在时返回 `{"error": ""}`，用户看到空提示；
  - `KeyError` 经 `str()` 后带引号（实测 `"'找不到数据表：abc'"`）。
- 建议：`next(..., default=None)` 或 `tableById` 式显式判空并抛带文案的 `ValueError`；内部错误改 500；`warehouse.load` 改用 `ValueError`/自定义异常。

### P3-2 Host 头不校验，来源检查在 DNS rebinding 下失效
- 位置：`server.py:553-555`
- 问题：POST 的 Origin 检查与 `Host` 拼接后比对（`'http://' + Host`）；DNS rebinding 攻击下 Host 与 Origin 都属于攻击者域，检查形同虚设；GET 请求则完全无来源检查，可读取全部已导入数据。
- 影响：仅监听 `127.0.0.1` 且现代浏览器有私网访问限制，实际风险低；但 README 支持门户部署，建议加固。
- 建议：请求入口校验 `Host ∈ {127.0.0.1:port, localhost:port, PUBLIC_ORIGIN}`。

### P3-3 `/api/raw` 疑似死接口，且存在 `max_row` 为 None 的崩溃路径
- 位置：`server.py:528-539`
- 问题：前端 `web/*.js` 与全部测试均无对 `/api/raw` 的调用（`/api/sheet` 已取代其职能）；read-only 工作簿在缺少 dimension 信息时 `sheet.max_row` 可能为 `None`，`min(start+79, sheet.max_row)` 会抛 `TypeError`。
- 建议：确认后删除；若保留则修 `max_row`/`max_col` 的 None 处理（可参考 `/api/sheet` 的 `sheet_layout`）。

### P3-4 `header()` 丢弃全部副标题参数（死参数/交互回归隐患）
- 位置：`web/app.js:46`（定义只接受 `eyebrow`）、调用点 `web/app.js:201`（compare）、`300`（saved）、`311`（search）、`385`（rawPage）
- 问题：调用方传入的第二、第三参数（页面说明、含 `state.query` 的搜索词展示）全部被静默丢弃。搜索页设计意图中的"搜索「关键词」"标题从未出现。
- 建议：让 `header()` 渲染副标题（需转义），或清理调用方参数。

### P3-5 `empty()` 模板不做转义，属潜在 XSS 缺口
- 位置：`web/app.js:52`
- 问题：`title`/`subtitle` 原样插入 HTML。当前所有调用点均手动 `esc()` 或传静态字符串，未构成实际漏洞；但该函数签名无任何"调用方必须先转义"的提示，新增调用极易踩坑（对比 `grid()`/`options()` 均内部转义）。
- 建议：与项目其他渲染函数保持一致，在 `empty()` 内部统一转义，按钮等富内容改由参数单独传递。

### P3-6 识别规则保存后写入空签名，必然触发一次冗余全量重解析
- 位置：`server.py:598`（`STORE._replace_file(..., '')`）
- 问题：保存手动识别规则后将该文件的 `file_versions.signature` 写为空串，下一次共享监控周期必定判定"文件已变化"并整体重新解析（结果与本应相同）。
- 影响：一次无谓的完整解析（对大文件即一次内存峰值）；期间若文件恰好被保存，用户需再等一个稳定窗口。
- 建议：规则保存流程中按真实签名写入，或显式跳过下一次对同一签名文件的重复解析。另建议校验 `payload.get('name')` 为字符串。

### P3-7 启动脚本与 README 的环境要求不一致
- 位置：`启动数据速查.cmd:39`、`README.md`（安装章节）、`requirements.txt`
- 问题：cmd 检查 `sys.version_info < (3, 10)`，README 写"Python 3.11 或更新版本"；cmd 将 `streamlit`、`plotly` 列为必需依赖，但主服务 `server.py` 并不需要它们（仅旧版入口 `app.py` 需要）。
- 影响：3.10 环境能通过脚本检查但可能违反文档约束；用户被强制安装仅旧入口使用的包。
- 建议：统一为 3.11+；将 streamlit/plotly 检查改为可选警告，或拆分 `requirements.txt`。

### P3-8 上传缺少总量与并发配额
- 位置：`server.py:151-221`（`import_workbook`）、`server.py:556-575`
- 问题：单个文件限 256 MiB，但无并发数限制、无磁盘总量配额；校验阶段完整解流工作簿，恶意压缩比（zip-bomb）工作簿可长时间占用线程。
- 影响：本机单人使用风险低；门户部署时依赖网关限制（README 已注明 256 MiB 代理上限）。
- 建议：限制并发导入数；校验阶段加超时或行数上限；记录导入失败时的临时文件清理（当前 `finally` 已处理，正常）。

### P3-9 `STATUS` 共享字典跨线程读写无锁
- 位置：`server.py:62`（定义）、`95`（`sync_worker` 更新）、`128-133`（`watch_shared` 更新）、`489`（读取合并）
- 问题：`errors`/`shared_errors`/`busy` 由多个线程读写，依赖 CPython dict/list 单操作原子性，无显式同步。当前读写模式（整体替换而非增量修改）下实际风险很小。
- 建议：维持现状可接受；如继续演进，可合并为单一状态对象并用 `SYNC_LOCK` 保护。

### P3-10 CSV 导出防公式注入覆盖不全
- 位置：`web/app.js:54`（`exportCSV` 仅拦截行首 `= + @`）
- 问题：常见向量已覆盖（tab 前缀是标准缓解手法），但行首 `%`、`|`、制表符后引导空格等变体未处理；部分表格软件对这些字符的处理不同。
- 影响：导出的 CSV 在 Excel 中打开时理论上可触发公式提示，实际需用户配合，风险低。
- 建议：按 OWASP CSV Injection 指南扩充拦截集合。

## 正面观察（值得保持的设计）

1. **SQL 安全**：所有查询参数化；动态标识符（表名/列名）经 `quote()` 双引号转义（`warehouse.py:195-206`）；表名来自内部摘要而非用户输入。
2. **路径安全**：静态服务跳过 `..` 组件；上传文件名校验完备（Windows 保留名、控制字符、`~$` 前缀、结尾点/空格）；`destination.is_symlink()` 检查；`build_release.py` 拒绝符号链接与 reparse point（`reject_links`）。
3. **上传完整性**：临时文件 → openpyxl 全量校验（含 `reset_dimensions()` 防声明天量空表）→ 原子发布；覆盖确认绑定 `dev:inode:size:mtime:ctime` 而非文件名，独占发布防"检查后出现同名文件"竞态（`server.py:137-221`）。
4. **同步语义**：稳定观察窗口（60s）+ 解析前后双签名复核 + 失败保留上次成功数据（`warehouse.py:149-171`）；`shared_sync.py` 对不可访问来源的处理正确。
5. **XXE 防护**：工作表 SAX 解析显式拒绝 DTD（`server.py:334-341`）。
6. **发布链路**：清单含逐文件 SHA-256，复制后回读校验，先写 payload 后写清单（中断的副本不可发布）（`scripts/build_release.py:111-143`）。
7. **测试**：89 项 Python + 12 个 Node 套件全部通过，覆盖导入、迁移、门户前缀、多来源扫描等关键回归。

## 建议处理顺序

1. P2-1（删除上传文件的永久报错）——影响日常体验，修复面小。
2. P3-1（错误处理）——与 P2-1 一起做，改善所有失败场景的提示。
3. P2-2（ECharts 升级）——独立进行，升级后全量回归前端测试。
4. P2-3 / P2-4（搜索与解析性能）——按数据规模增长情况排期。
5. 其余 P3 可随日常迭代顺手清理。
